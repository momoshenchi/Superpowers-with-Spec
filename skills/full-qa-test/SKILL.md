# Full QA Test — 六维立体覆盖

对测试对象做无死角拆解：按固定 Step **逐维**产出用例，禁止跳步、禁止六维混写成一坨。

## When to Use

- 变更提案处于 verify 阶段 / PR 合并需要测试方案或用例
- 发布前担心漏测、要做覆盖自查
- 用户提到：无死角、全覆盖、六维、边界/状态机/并发/降级/变异测试

违反即视为未完成：跳过某一维、只写 Happy Path、用「应该差不多」代替 Checklist。

## principle

执行 `full-qa-test` 各 Step 时按需查阅本文件。维度互补，缺一不可。

```
                    ┌──────────────────────────┐
                    │  1. 需求与业务场景覆盖率   │
                    └────────────┬─────────────┘
                                 │
     ┌───────────────────────────┼───────────────────────────┐
     ▼                           ▼                           ▼
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│2.代码与分支覆盖│         │3.数据与边界覆盖│         │4.状态与时序覆盖│
└──────────────┘         └──────────────┘         └──────────────┘
     │                           │                           │
     └───────────────────────────┼───────────────────────────┘
                                 │
                    ┌────────────┴─────────────┐
                    │ 5. 非功能与防错覆盖 (质量) │
                    └────────────┬─────────────┘
                                 │
                    ┌────────────┴─────────────┐
                    │6. 环境与上下文依赖覆盖率 │
                    └──────────────────────────┘
```

<Core-principle> 
没有走完六维 Step + 自查 Checklist，就不能声称「覆盖充分」。
如果在测试计划设计阶段, 不需要等待测试结果
如果在测试覆盖阶段, 验证阶段, 必须完成各个step的全部动作, 且测试全部通过才可进入下一阶段(除非该测试无法执行或不适用)
</Core-principle> 


## Progress Tracker（必须复制并勾选）

开始前把下面清单贴到回复中，**完成一维勾一项，再进入下一维**：

```
六维覆盖进度:
- [ ] Step 0 锁定测试对象
- [ ] Step 1 需求与业务场景
- [ ] Step 2 代码与分支
- [ ] Step 2b 变异测试（测试质量门禁）
- [ ] Step 3 数据与边界
- [ ] Step 4 状态与时序
- [ ] Step 5 非功能与防错
- [ ] Step 6 环境与依赖
- [ ] Step 7 自查 Checklist
- [ ] Step 8 交付测试矩阵
```

每完成一维：先输出该维的用例表，再勾选对应 Step，然后才进入下一维。

---

## Step 0 — 锁定测试对象

**目标：** 明确「测什么」，避免后续维度空转。

**必须产出：**
1. 测试对象（模块 / API / 页面 / 变更 diff）
2. 输入来源（PRD / 代码 / OpenAPI / 用户描述）
3. 一句话风险假设（最可能漏测什么）

不足信息时先问清，再进入 Step 1。

---

## Step 1 — 需求与业务场景覆盖

**目标：** 做对的事情，防需求漏测。

**逐步动作：**
1. 列出正向主流程（Happy Path）价值链
2. 列出分支 / 异常流（取消、失败、中断后重入）
3. 建 RTM：`需求项 → N 条用例`（每条需求至少 1 条）
4. 补隐性需求（防重复提交、跨页状态留存等常识逻辑）

**本步产出表列：** `ID | 需求项 | 场景类型(正向/分支/异常/隐性) | 步骤 | 预期 | 维度=D1`

勾选 Step 1 后进入 Step 2。

---

## Step 2 — 代码与分支覆盖

**目标：** 白盒验证控制流，防未执行代码藏 Bug。

**逐步动作：**
1. 标出关键路径上的分支点（if/else、switch、早返回、catch）
2. 为每个判定补 True / False（至少 Branch）
3. 多条件表达式：标出需组合覆盖的条件（高风险再用 Condition Combo / MC/DC）
4. 若有 Git 变更：优先 **Diff Coverage**（本次改动行必须有对应用例）

**本步产出表列：** `ID | 代码锚点(文件:符号/分支) | 覆盖类型 | 触发输入 | 预期 | 维度=D2`

勾选 Step 2 后进入 Step 2b（有可运行测试时）；若本轮仅产出用例矩阵、尚无自动化，可标注「2b 延后」并进入 Step 3，但不得声称 D2 测试质量已验证。

---

## Step 2b — 变异测试（测试质量门禁）

**目标：** 检验用例是否真能抓住缺陷，揭穿「行覆盖高但断言弱」的假覆盖。属于 **D2 的覆盖质量验证**，不是新需求发现手段。

**前置条件（全部满足才跑）：**
1. Step 2 用例已落地为可执行测试（单元/组件优先）且全部通过（All Green）
2. 测试能红能绿，且含有意义的 Assert（不只是「不抛错」）
3. 行/分支或 Diff 覆盖已达当前约定门槛

**逐步动作：**
1. 应用变异算子（Apply Mutation Operators），制造突变体
2. 针对每个变异体运行测试（Run Tests against Mutants）
3. 判定变异体状态（Determine Mutant Status）, 计算变异得分
    - 变异得分 (Mutation Score)= 被杀死的变异体数 (Killed)/ (生成的总有效变异体数 (Total Valid Mutants)− 等价变异体数 ) 
​4. 分析幸存体与排查“等价变异体”

**本步产出：**
- 变异范围（文件/符号）
- 变异得分 + 存活 mutant 列表（各附补测用例 ID 或「等价变异/可忽略」理由）
- 是否达到门禁（未达则不得勾选 2b）

勾选 Step 2b 后进入 Step 3。发布前可对 Diff 核心模块再跑一次轻量变异，结果并入 Step 7/8。

---

## Step 3 — 数据与输入空间覆盖

**目标：** 防特殊数据崩溃与注入。

**逐步动作：**
1. 对每个输入参数做等价类 + BVA（N-1, N, N+1、空、Null、超长）
2. 多参数交互用 pairwise / 正交，避免笛卡尔爆炸
3. 对脏数据测试：SQL/XSS、Emoji、反斜杠、Unicode 特殊字符

**本步产出表列：** `ID | 参数 | 等价类/边界/脏数据 | 输入样例 | 预期 | 维度=D3`

勾选 Step 3 后进入 Step 4。

---

## Step 4 — 状态变迁与时序覆盖

**目标：** 防非法状态跳跃、竞态、超时重试导致混乱。

**逐步动作：**
1. 画出合法状态与转换（矩阵或列表）
2. 为每条**非法跳跃**设计拒绝/无副作用用例
3. 并发：快速双击、多端同资源
4. 超时与重试：HTTP 超时、MQ 重复投递、幂等性

**本步产出表列：** `ID | 状态/时序场景 | 合法? | 操作序列 | 预期 | 维度=D4`

勾选 Step 4 后进入 Step 5。

---

## Step 5 — 非功能与防错覆盖

**目标：** 稳、快、安全，不只是「能跑」。

**逐步动作（按对象裁剪，但须显式说明跳过理由）：**
1. 性能：峰值 / 稳态 / 容量（至少标出是否适用）
2. 安全：水平/垂直越权、未授权访问、敏感数据脱敏
3. 容灾：断网、依赖宕机、DB 延迟、第三方 502/504
4. 兼容：OS / 浏览器 / 分辨率 / 弱网（若适用）

**本步产出表列：** `ID | 质量属性 | 场景 | 判定标准 | 预期 | 维度=D5`

勾选 Step 5 后进入 Step 6。

---

## Step 6 — 环境与上下文依赖覆盖

**目标：** 防微服务「蝴蝶效应」。

**逐步动作：**
1. 列出上下游依赖（HTTP / MQ / DB / 缓存 / 第三方）
2. 下游延迟/故障：熔断、降级、超时是否生效
3. 数据一致性：分布式事务失败补偿（TCC/Saga 等）是否生效
4. 空数据 / 缓存未命中 / 依赖返回异常时的上游行为

**本步产出表列：** `ID | 依赖 | 故障注入 | 期望隔离/补偿 | 预期 | 维度=D6`

勾选 Step 6 后进入 Step 7。

---

## Step 7 — 无死角自查 Checklist

对照下表逐项勾选；未覆盖项必须补用例或写明「不适用 + 理由」：

| 维度 | 必查项 | 覆盖? | 补充用例 ID / 说明 |
|------|--------|-------|-------------------|
| 功能 | 1. 正向主流程及所有分支逻辑 | [ ] | |
| 功能 | 2. 异常中断后恢复机制 | [ ] | |
| 代码 | 3. Diff/关键路径分支覆盖 + 变异测试（或「延后/不适用」理由） | [ ] | |
| 数据 | 4. 边界值（最大/最小/0/负/空串/Null） | [ ] | |
| 数据 | 5. 特殊字符、超长、Emoji、SQL/XSS | [ ] | |
| 状态 | 6. 状态机非法路径（越权/逆向切换） | [ ] | |
| 状态 | 7. 并发请求及幂等（双击/重放） | [ ] | |
| 依赖 | 8. 第三方超时/5xx 时降级兜底 | [ ] | |
| 依赖 | 9. DB/缓存为空或异常时的逻辑 | [ ] | |
| 环境 | 10. 弱网（高延迟/高丢包/无网） | [ ] | |
| 环境 | 11. 多终端/分辨率/权限角色兼容 | [ ] | |

任一项未勾且无「不适用」理由 → 回到对应 Step 补齐。

勾选 Step 7 后进入 Step 8。

## Step 8 — 交付输出包

### 六维用例总表 — 示例（格式示范，交付时替换为 Step 0–6 实际产出）

> 测试对象：`POST /api/orders/{id}/cancel`（订单取消 API；Diff 涉及 `OrderService.cancel`）

| ID | 维度 | 测试目标 | 输入/前置 | 步骤 | 预期 |
|----|------|----------|-----------|------|------|
| TC-D1-001 | D1 | REQ-取消-01：待支付订单可取消（正向） | 订单 status=pending，归属当前用户 | 1. 登录 2. POST cancel | 200；status→cancelled；返回取消时间 |
| TC-D1-002 | D1 | REQ-取消-02：已发货不可取消（分支） | 订单 status=shipped | 1. POST cancel | 409；code=ORDER_NOT_CANCELLABLE；status 不变 |
| TC-D1-003 | D1 | REQ-取消-03：中断后可重试取消（异常） | pending 订单；首次 cancel 网络中断 | 1. 查 status 仍为 pending 2. 再次 POST cancel | 第二次 200；最终 cancelled；无重复退款 |
| TC-D1-004 | D1 | 隐性：防重复提交 | 同一 pending 订单 | 200ms 内连续 POST cancel 两次 | 仅一次生效；第二次幂等或 409 |
| TC-D2-001 | D2 | orderService.ts:cancel — status===shipped 分支 True | orderId 有效；DB status=shipped | 调用 cancel(orderId) | 早返回/抛 ORDER_NOT_CANCELLABLE；不调用 payment.refund |
| TC-D2-002 | D2 | orderService.ts:cancel — refund 失败 catch | pending；mock refund 抛 PaymentError | 调用 cancel | 无半取消；502；status 保持 pending 或回滚 |
| TC-D3-001 | D3 | orderId — 空串边界 | orderId="" | POST /api/orders//cancel | 404 或 400；不访问 DB |
| TC-D3-004 | D3 | reason — 超长 BVA（max=200, N+1） | reason=201 字符 | POST cancel + body.reason | 400 字段校验失败 |
| TC-D4-001 | D4 | pending→cancelled（合法） | status=pending | cancel | status=cancelled |
| TC-D4-002 | D4 | shipped→cancelled（非法跳跃） | status=shipped | cancel | 拒绝；status 仍为 shipped |
| TC-D5-001 | D5 | 安全：垂直越权 | 用户 A 订单；用户 B token | B 调用 cancel A 的 orderId | 403 FORBIDDEN |
| TC-D5-002 | D5 | 容灾：payment 超时 | payment 延迟 30s | POST cancel | 504/超时；无半取消状态 |
| TC-D6-001 | D6 | payment-service — refund 502 | mock payment 502 | POST cancel pending 订单 | 错误上抛；可重试；无脏数据 |

### 输出格式

**最终回复必须包含（按此顺序）：**

1. **对象与风险摘要**（来自 Step 0）
2. **六维用例总表**（合并 D1–D6，列：`ID | 维度 | 测试目标 | 输入/前置 | 步骤 | 预期`）
3. **RTM**（需求 → 用例 ID 列表）
4. **自查 Checklist**（Step 7 已填）
5. **自动化骨架**（可选但推荐）：AAA 格式，含断言；优先覆盖 P0（主流程、非法状态、幂等、依赖降级）
6. **变异测试结果**（若执行了 2b）：范围、杀伤率、存活 mutant 与补测 ID；未跑则写「延后/不适用 + 理由」
7. **残留风险**：明确未自动化 / 需人工 / 环境受限 / 未杀死 mutant 项

完成后勾选 Step 8。未完成进度清单不得声称「全覆盖完成」。


## Common Mistakes

| 错误 | 纠正 |
|------|------|
| 六维一次写完、无进度勾选 | 停：按 Step 1→6 逐维输出并勾选 |
| 只有 Happy Path | 强制补异常流 + 非法状态 + 脏数据 |
| 跳过 D2 因为「黑盒」 | 至少标关键分支与 Diff 改动点 |
| 无测试/无断言就跑变异 | 先完成 Step 2 可执行用例与覆盖门槛，再进 2b |
| 在 E2E/混沌阶段做全仓变异 | 仅对 Diff/核心单元测试层做；场景维靠 D3–D6 设计 |
| Checklist 全勾但无用例 ID | 每项必须挂用例 ID 或「不适用+理由」 |
| 忽略依赖故障 | D5/D6 至少各有一条故障注入 |
