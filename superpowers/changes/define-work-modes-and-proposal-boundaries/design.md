## Context

Superpowers currently has a proposal-driven default narrative, but users also need a proportional path for small, unambiguous edits. At the other end of the scale, a single Proposal can become too large for reliable autonomous execution: the coordinator and workers repeatedly reread unrelated surfaces, context is compressed and reconstructed, and quality drops even when the individual tasks are reasonable. The design therefore treats a Change Proposal as an agent workload/context budget, while retaining Dispatch Units as the implementation ownership and parallelism boundary inside one change.

This is a guidance, static-skill, and CLI distribution change. It does not alter product application runtime behavior, Superpowers artifact schemas, or API/state/error surfaces.

## Current system

The root workflow guidance lives in `skills/using-superpowers/SKILL.md`. Proposal artifacts and their execution requirements are generated by the `spec-driven` schema in `schemas/spec-driven/`, with `tasks.md` top-level headings representing logical Dispatch Unit boundaries and `execution-plan.md` providing ownership, dependencies, and handoff guidance. The existing Verify behavior is documented in `superpowers/specs/sp-verify-skill/spec.md`; this change adds the missing report-first/coordinator-repair contract as a delta.

`skills/subagent-driven-development/SKILL.md` defines Dispatch Unit execution and one final cross-unit review. `skills/requesting-code-review/SKILL.md` currently mixes generic review dispatch with an outdated `/sp:apply` batch cadence; its `code-reviewer.md` is the reviewer prompt. `skills/receiving-code-review/SKILL.md` evaluates incoming feedback. `skills/verification-before-completion/SKILL.md` is the evidence-before-claims guardrail.

`src/core/templates/workflows/apply-change.ts` and `src/core/templates/workflows/final-quality-gates.ts` define Apply's Test Hardening and final gate sequence. Apply already owns the mandatory final sequence of host-native code review, Simplify, Verify, and Design Verify. Static skills under `skills/` are copied into configured tool directories by the bundled-asset path in `src/core/init.ts`. `src/core/update.ts` currently refreshes generated Superpowers workflow skills and commands, but does not synchronize bundled static skills; this change extends the refresh path so the renamed static skill and obsolete-directory cleanup reach existing Claude Code, Codex, OpenCode, and other configured installations. Generated workflow skills remain managed separately by `src/core/shared/skill-generation.ts`.

## Goals / Non-Goals

**Goals:**

- Support exactly two execution modes: Direct Modification and Proposal → Review → Apply.
- Make a user-requested plan an execution aid under the selected mode, not a third lifecycle.
- Decide Proposal creation from risk and estimated agent workload rather than prompt length or file count alone; a new externally visible capability or public contract remains a Proposal trigger even when its implementation score is small.
- Provide a concrete workload rubric that accounts for code surface, layers, behavior complexity, verification, orchestration, and context churn.
- Permit multiple small fixes or features in one Proposal when their combined workload fits the budget.
- Split multiple genuinely large capabilities, or a single over-large capability with stable milestones, into bounded Proposals before creating their Dispatch Units.
- Preserve the distinction between a Proposal's context/archive boundary and a Dispatch Unit's ownership/parallelism boundary.
- Give autonomous agents a repeatable decomposition process for multi-session and very large requests.
- Rename and refocus the generic code-review dispatch skill so it does not duplicate Apply's final-quality orchestration.
- Make the agreed repair ownership explicit: read-only code review/Verify/Design Verify by default, safe self-editing for Simplify, and coordinator-owned repairs where product intent or architecture is involved.

**Non-Goals:**

- Do not introduce a third Plan Mode, plan artifact, or new schema.
- Do not change the existing Proposal artifact graph or the meaning of `tasks.md` and `execution-plan.md`.
- Do not create a Superpowers `code-review` command or replace host-native code review.
- Do not define or implement a new subagent context-packet protocol in this change.
- Do not change product code, public APIs, database schemas, or runtime behavior.
- Do not require every independent feature to have its own Proposal when the combined workload is small.

## Decisions

### 1. Work-mode model

**Problem:** The workflow must support small direct edits without weakening the Proposal path for high-risk or large work.

| Option | Complexity | Small-task experience | Large-task safety | Trade-off |
|---|---|---|---|---|
| A. Proposal for every change | Low runtime branching | Excessive artifacts for tiny fixes | Strong | High process/context overhead and unnecessary fragmentation. |
| B. Direct, Plan, and Proposal as three separate lifecycles | Medium | Flexible | Strong | Adds a third state machine and makes “plan then edit” semantics ambiguous. |
| C. Direct Modification plus Proposal → Review → Apply | Low | Proportional | Strong when risk/workload triggers Proposal | A plan is conversational rather than durable unless Proposal criteria are met. |

**Choice:** C. Explicit user instructions select the mode when they are compatible with risk; otherwise the agent uses the risk/workload rules. A plan requested before a low-risk edit does not create a third lifecycle. Crossing a Proposal boundary promotes the work before further writes.

**Trade-offs / cost:** Direct work has fewer durable artifacts, so the completion evidence rules and promotion triggers must be explicit. Proposal work retains the full artifact and gate overhead where it buys context and correctness.

### 2. Proposal boundaries are workload-first

**Problem:** Independent releaseability alone would split small fixes too aggressively, while feature-only grouping would leave multiple large capabilities in one context-heavy Proposal.

| Option | Primary boundary | Small unrelated fixes | Multiple large capabilities | Context protection |
|---|---|---|---|---|
| A. Lifecycle-first | Release, rollback, and ownership | Often fragments them | May still combine too much | Medium |
| B. Feature-per-Proposal | One capability per change | Over-fragments | Protects context | Low for small fixes |
| C. Workload-budget-first | Agent effort and context churn, with risk/lifecycle guardrails | Combines when budget allows | Splits when large or over budget | High |

**Choice:** C. Estimate each logical capability on six 0–3 dimensions: implementation surface, layer breadth, behavior complexity, verification cost, orchestration cost, and context churn. Use the combined workload as the primary Proposal budget. Public-contract, migration, security, data-integrity, and other high-risk work still requires a Proposal regardless of score.

Default bands are `0–5` small, `6–10` medium, `11–14` large, and `15+` very large. They are calibration guidance rather than a mechanical file-count gate. Use the following anchors for each 0–3 dimension: `0` means no meaningful contribution, `1` means one local and familiar surface, `2` means several related surfaces or one non-trivial risk, and `3` means broad/cross-boundary work or a high-uncertainty path. Sum the dimensions for each logical capability, then sum compatible capabilities for the Proposal budget; count a shared foundation once at the boundary where it is actually implemented. A Proposal normally targets a combined score of `14` or less, no more than `3–5` Dispatch Units, and no more than `2–3` dependency waves. Exceeding any soft limit triggers reevaluation and likely splitting, while a necessary atomic boundary may override a numeric signal.

Splitting rules:

- Multiple small or medium capabilities remain in one Proposal when their combined workload fits the budget and a single acceptance narrative is practical.
- Two or more large capabilities normally become separate Proposals, even if they could theoretically ship together.
- One very large capability is split into stable, testable milestone Proposals when possible; otherwise it remains one Proposal with explicit staged Dispatch Units and must not absorb other large capabilities.
- A large capability may absorb a small adjacent fix when that fix does not add a separate coordination or verification burden.
- Shared foundation work is a separate Proposal only when it is independently testable and substantial; otherwise it belongs to the first dependent Proposal and is recorded as a prerequisite for later ones.

**Trade-offs / cost:** Workload estimation is approximate and needs judgment. The benefit is avoiding context rot without forcing every small cross-feature fix into separate lifecycle overhead.

### 3. Change versus Dispatch Unit

**Problem:** Large requests need internal parallelism without making every agent assignment an independently archivable change.

| Option | Unit means | Archive boundary | Context benefit |
|---|---|---|---|
| A. Every unit is a Proposal | Feature or file slice | Each unit | Strong but excessive lifecycle overhead and fragmented acceptance. |
| B. One Proposal with no units | Entire request | One change | Simple but unsafe for large implementations and parallel work. |
| C. Workload-bounded Proposals containing logical Dispatch Units | Proposal protects context; unit protects ownership | Proposal only | Preserves coherent acceptance while enabling safe delegation. |

**Choice:** C. First partition a request into workload-bounded Proposals; then divide each Proposal into logical Dispatch Units by ownership, dependency, and safe parallelism. A Dispatch Unit is not a live subagent identity, not a checkbox-sized timebox, and not independently archivable.

**Trade-offs / cost:** A Proposal can still contain several units and may require multiple sessions. The execution plan must keep ownership and dependency evidence precise enough that workers do not rediscover the whole request.

### 4. Code-review skill identity and scope

**Problem:** `requesting-code-review` sounds like a review implementation and currently contains a stale `/sp:apply` “every 3 tasks” rule, while Apply already owns final review orchestration.

| Option | Compatibility | Naming clarity | Duplicate-review risk |
|---|---|---|---|
| A. Keep `requesting-code-review` | Highest | Mixed: request and cadence | High unless carefully rewritten |
| B. Keep old name with a new alias | Medium | Two discoverable names | High; agents may invoke both |
| C. Rename to `when-to-dispatch-code-review` and update live references | Requires refreshed installations | Explicitly describes timing and boundaries | Lowest |

**Choice:** C. Rename the static skill directory and frontmatter, update live references and guidance tests, and refresh installed copies through the normal update flow. Do not retain a duplicate alias. The skill will cover when to dispatch, mode-specific timing, reviewer input/output, and duplicate prevention; it will not implement a Superpowers code-review workflow.

**Trade-offs / cost:** Existing installed copies need a normal Superpowers update. Historical archived artifacts may retain their historical path references; live guidance and tests must use the new name.

### 5. Repair ownership

**Problem:** Review workers, cleanup workers, and verification workers have different incentives and different kinds of findings.

| Option | Reviewer edits | Independence | Simplicity |
|---|---|---|---|
| A. Every gate worker self-repairs | All findings repaired by worker | Lowest | Simple wording, high self-approval risk |
| B. Coordinator repairs everything | All workers report only | Highest | Clear but makes safe cleanup slower |
| C. Gate-specific hybrid | Simplify may self-edit safe cleanup; review/Verify/Design Verify report; coordinator repairs product/architecture/UI | High where it matters | Requires explicit matrix |

**Choice:** C. Host-native code review, Verify, and Design Verify are read-only by default; the coordinator repairs their findings and starts the relevant fresh review round. Simplify may apply behavior-preserving cleanup, but must revert or skip uncertain changes. `receiving-code-review` remains the coordinator's technical feedback-evaluation protocol.

**Trade-offs / cost:** Some safe fixes require an extra coordinator step, but reviewer independence and product-intent ownership are clearer.

## Risks / Trade-offs

- [Workload estimates vary by repository and model] → Treat score bands as calibration signals, keep risk overrides mandatory, and review the proposed partition before creating multiple changes.
- [A very large capability may not have stable intermediate milestones] → Keep it as one Proposal with explicit staged Dispatch Units rather than inventing artificial changes; prohibit adding other large capabilities.
- [Renaming the static skill leaves stale installed copies] → Make init/update synchronize bundled static assets and explicitly remove the obsolete installed directory before verifying no live reference or configured tool root exposes the old path.
- [Apply, SDD, and standalone review may still be invoked twice] → Make Apply the only mandatory final-gate owner inside Apply, keep one final SDD integration review when SDD is standalone, and remove the old per-batch Apply rule.
- [Direct work may silently grow] → Add promotion triggers: new public contracts, risky data/security behavior, multiple large surfaces, multiple dependency waves, or workload exceeding the Proposal budget pauses direct work and creates a Proposal.

2. Rename and rewrite the code-review dispatch skill and reviewer prompt; update live references and static guidance tests.
