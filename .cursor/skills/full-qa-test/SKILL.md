# Full QA Test — 六维立体覆盖

对测试对象做无死角拆解：按固定 Step **逐维**产出用例，禁止跳步、禁止六维混写成一坨。

## When to Use

独立调用与 Superpowers 变更共用同一套 Step，缺少 spec 或变更提案不是拒绝执行的理由。

- 用户直接要求无死角 / 全覆盖 / 六维 / 测试方案或用例（PRD、代码、API、口述均可开工）
- 发布前、PR 合并前担心漏测、要做覆盖自查
- Superpowers 变更的 `test-plan` / Test Hardening / Verify
- 用户提到：无死角、全覆盖、六维、边界/状态机/并发/降级/变异测试

违反即视为未完成：跳过某一维、只写 Happy Path、用「应该差不多」代替 Checklist、只把书面需求原文转换成用例就停。

## principle

执行 `full-qa-test` 各 Step 时按需查阅本文件。维度互补，缺一不可。

```
                    ┌──────────────────────────┐
                    │  1. 需求与业务场景覆盖率   │
                    └────────────┬─────────────┘
                                 │
     ┌───────────────────────────┼───────────────────────────┐
     ▼                           ▼                           ▼
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│2.代码与分支覆盖│         │3.数据与边界覆盖│         │4.状态与时序覆盖│
└──────────────┘         └──────────────┘         └──────────────┘
     │                           │                           │
     └───────────────────────────┼───────────────────────────┘
                                 │
                    ┌────────────┴─────────────┐
                    │ 5. 非功能与防错覆盖 (质量) │
                    └────────────┬─────────────┘
                                 │
                    ┌────────────┴─────────────┐
                    │6. 环境与上下文依赖覆盖率 │
                    └──────────────────────────┘
```

<Core-principle> 
没有走完六维 Step + 自查 Checklist，就不能声称「覆盖充分」。
如果在测试计划设计阶段, 不需要等待测试结果
如果在测试覆盖阶段, 验证阶段, 必须完成各个step的全部动作, 且测试全部通过才可进入下一阶段(除非该测试无法执行或不适用)
Step 1–6 产出用例时，必须遵循下方「10→10→10 分批覆盖法」。
</Core-principle> 

## 10→10→10 分批覆盖法

**适用：** Step 1–6 产出用例时强制执行，**以「测试对象 × Step」为单位**——每个已登记对象在每个 Step 各独立跑一轮 10→10→10。Step 0 / 7 / 8 / 9 不适用。

**核心规则：** 针对当前对象、当前 Step，先编写 **10 条**用例；若本批经去重后仍有逻辑上非重复的有效用例，再编写 **10 条**；以此类推，**单对象单维最多 30 条**。

### 执行流程

1. **批次 1（必做）：** 针对当前对象，严格按本 Step「逐步动作」产出 10 条用例，覆盖该对象在本维的 P0 / 核心场景。Step 1 先导入该对象已有的书面 Scenario（spec `#### Scenario:` / PRD / ticket / 用户列出的验收），导入条数计入这 10 条，不够再补 `gap:`。没有书面 Scenario 时直接手工拆，不要停工。
2. **去重审查：** 逐条对照本对象本维已有用例，判定逻辑是否重复
3. **批次 2（条件允许）：** 若批次 1 去重后 **≥1 条** 为有效新增 → 再产出 10 条，覆盖次要分支 / 边界 / 组合
4. **批次 3（条件允许）：** 若批次 2 去重后 **≥1 条** 为有效新增 → 再产出 10 条，覆盖长尾 / 罕见 / 交叉场景
5. **停止条件（满足任一即停，换下一个对象；本 Step 全部对象跑完才进入下一 Step）：**
   - 本对象本维累计已达 30 条
   - 当前批次去重后 **0 条** 有效新增（无法产出非重复用例）
   - 本对象在本维的动作项已全部覆盖且无合理扩批空间（须写明理由）
   - 本对象在本维确实不适用（写明「R<n> 本维不适用 + 理由」占位，不算欠账）

### 关于体量

对象数 × 6 维 × 至少 10 条会迅速膨胀，这是「无死角」的代价，但**不是要求你凑数**。对象拆得越细，单个对象在某一维的动作项就越容易在批次 1 内穷尽，从而合法触发停止条件。去重规则永远优先于条数：宁可写明「批次 1 仅 6 条，本对象本维动作项已穷尽」，也不要制造 4 条逻辑重复用例把数字填到 10。

### 逻辑重复判定（去重标准）

两条用例视为**逻辑重复**，当且仅当同时满足：

- **输入语义相同**（等价输入 / 等价前置，含边界同类）
- **触发路径相同**（同一操作序列或同一代码分支）
- **断言焦点相同**（验证同一行为 / 同一失败模式）

仅改措辞、换 ID、或只改非关键字段值 → 不算新用例。去重后删除或合并重复项，再计数是否扩批。

### 每 Step 分批进度（产出用例时复制勾选）

```
对象 R<n> · Step N 分批进度:
- [ ] 批次 1 — 10 条（必做）
- [ ] 去重审查 — 有效新增: __ 条 / 剔除重复: __ 条
- [ ] 批次 2 — 10 条（去重后仍有新增才做）
- [ ] 去重审查 — 有效新增: __ 条 / 剔除重复: __ 条
- [ ] 批次 3 — 10 条（去重后仍有新增才做）
- [ ] 去重审查 — 有效新增: __ 条 / 剔除重复: __ 条
- [ ] 本对象本步合计: __ 条（上限 30）— 停止原因: __
```

每批产出后先输出该批用例表 + 去重结论，再决定是否进入下一批；一个对象跑完换下一个对象；本 Step 全部对象跑完后，再勾选 Progress Tracker 对应 Step。

## 测试形式选择

每条用例都必须标注**形式**，取值：`unit` / `integration` / `E2E` 。不标形式的用例无法排期，也看不出证据该长什么样。

**选择原则：能在低层观察到的行为就在低层测。** 只有当行为在低层根本不显现时才上移一层，并在用例里说明为什么必须上移。为了"更真实"把本可单测的分支写成 E2E，是拖慢反馈、制造脆弱用例的主要原因。

| 维度 | 默认形式 | 何时上移 |
|------|----------|----------|
| D1 需求与业务场景 | integration | 价值链跨多个服务，或只有经 UI 才能观察到 → E2E |
| D2 代码与分支 | unit | 分支只有接入真实依赖后才可达 → integration |
| D3 数据与输入空间 | unit | 校验发生在框架/网关层而非被测函数内 → integration |
| D4 状态变迁与时序 | integration | 并发与幂等需要真实存储或队列；跨端竞态 → E2E |
| D5 非功能与防错 | integration | 性能与容量 → 专门压测；兼容性与弱网 → E2E |
| D6 环境与上下文依赖 | integration（故障注入 / 契约测试） | 熔断降级只在完整拓扑下可观察 → E2E |



## Progress Tracker（必须复制并勾选）

**每个step中， 完成一维勾一项，再进入下一维**：

```
六维覆盖进度:
- [ ] Step 0 锁定测试对象
- [ ] Step 1 需求与业务场景
- [ ] Step 2 代码与分支
- [ ] Step 3 数据与边界
- [ ] Step 4 状态与时序
- [ ] Step 5 非功能与防错
- [ ] Step 6 环境与依赖
- [ ] Step 7 变异测试（全部 unit 用例绿后）
- [ ] Step 8 自查 Checklist
- [ ] Step 9 交付测试矩阵
```

每完成一维：对每个已登记对象各跑一轮 **10→10→10**（含分批进度与去重结论），全部对象跑完再勾选对应 Step，然后才进入下一维。Step 7 变异测试接在 Step 6 之后，不是第 2 维的尾巴：执行时机在 Step 1–6 里所有 `form=unit` 用例落地且全绿之后。设计阶段只写矩阵时，Step 7 标「延后」并继续 Step 8，但不得声称测试质量已验证。

## Step 0 — 锁定测试对象

**目标：** 明确「测什么」，避免后续维度空转。本技能可独立使用（PRD / 代码 / API / 用户口述），也可在 Superpowers 变更的 test-plan / Hardening / Verify 中使用。有书面需求时优先复用其编号；没有书面需求时从入口和代码拆对象。不要因为缺少 spec 或变更提案而拒绝执行。

**必须产出：**
1. 输入来源（手头有什么写什么：delta spec / 主 spec / PRD / ticket / OpenAPI / 代码 / 用户描述）
2. **测试对象登记表**（见下）——把测试范围拆成可独立指认的对象，逐个编号
3. 每个对象一句话风险假设（最可能漏测什么）

### 如何选定对象

按可用性选用，从上到下碰到就能开工：

1. **有 Superpowers delta spec 或同等 `### Requirement:` 文档：** 对象取自那些 Requirement，编号 R1…Rn；不要另造一套平行功能编号。已有 `#### Scenario:` 是导入基线，不是天花板。
2. **有 PRD / ticket / OpenAPI / 用户列出的能力：** 一条可独立验收的能力一个对象，编号同样 R1…Rn。已写验收场景记入「已有 Scenario」。
3. **只有代码或入口：** 按可调用表面拆对象（路由、CLI 子命令、导出函数、UI 路由）。需求项写能力名。

书面需求写不全时仍须完善用例，而不是只做原文转换：

- 已有 Scenario 全部导入 D1（`imported:`），再按 10→10→10 补 `gap:`（正向 / 分支 / 异常 / 隐性）
- 书面需求漏掉、但 design / 代码 / 用户描述里能指认的整块能力：续编 `R<n>`，风险假设写明来源（如 `derived: 代码 / spec omitted`）。不要把漏写当成「不测」
- 本技能不负责改写 spec / PRD。在 Superpowers 变更里把「spec 未覆盖」记在风险假设，交给 specs 工件去补

对象不是文件、不是目录、也不是 Scenario。五层不要混用：

| 层 | 是什么 | 记在哪 |
|----|--------|--------|
| 对象 `R1` | 一条可独立指认的需求/能力的稳定 ID。有 `### Requirement:` 时用它；否则用能力名对应的 Rn | 登记表「对象」列；所有 `TC-R…` ID 的前缀 |
| 需求项 | 该能力名称 | 登记表「需求项」列。有 spec 抄标题；无 spec 写能力名，不要空着 |
| 系统被测 / 入口 | 真正能调到的表面 | HTTP 路由 / CLI 子命令 / 导出函数 / UI 路由，不是内部 helper |
| 已有 Scenario | 书面已写的验收场景（spec `#### Scenario:` / PRD 场景 / ticket 验收） | 导入清单；不是第二套对象 |
| 用例 | 一条可执行的 D1–D6 行 | `TC-R<n>-D<m>-<seq>` |

已有 Scenario 是需求方已经构思好的验收场景时，**它们就是 D1 的现成基线**：Step 1 直接导入，不要换个说法再写一次。六维的价值在于找出这些 Scenario **没覆盖到**的部分。没有书面 Scenario 时，Step 1 从入口和代码手工拆，D1 可以全是 `gap:`。

叫不出入口的行还不是测试对象：拆对象，或把入口标成「不适用」并写明为什么没有运行时表面。

### 测试对象登记表（必须产出）

**不登记就直接写用例，是后续「不知道这条在测什么」的根因。** 只有一个对象时也要登记一行。

| 对象 | 需求项 | 已有 Scenario | 入口 | Diff 锚点 | 风险假设 |
|------|--------|---------------|------|-----------|----------|
| R1 | `Requirement: 订单取消` | 3 条：待支付可取消 / 已发货拒绝 / 中断后可重试 | `POST /api/orders/{id}/cancel` | `orderService.ts:cancel` | 退款失败时留下半取消状态 |
| R2 | `Requirement: 取消原因审计` | 1 条：取消成功写审计 | `AuditLog.record`（由 R1 触发） | `auditLog.ts:record` | 取消成功但审计静默失败，无人发现 |

- **需求项**：有 spec 时抄 Requirement 原名，便于回溯；无 spec 时写能力名
- **已有 Scenario**：该对象下已写好的验收场景条数与要点（spec / PRD / ticket / 用户列出），Step 1 的导入清单；没有则写「无书面 Scenario」
- **入口**：外部真正能调到它的地方（HTTP 路由 / CLI 子命令 / 导出函数 / UI 路由），不是内部实现名
- **Diff 锚点**：有 git/PR diff 时填本次改动的文件或符号；独立测现有功能、没有本次 diff 时填被测符号，或写「无本次 diff，测现有代码」
- 对象之间若有触发关系（如 R1 触发 R2），在风险假设里点明。派生对象在风险假设里写来源（`derived: 代码 / spec omitted`）

### 用例 ID 规范

Step 1–6 的每条用例 ID 一律为 `TC-R<对象号>-D<维度号>-<序号>`，例如 `TC-R2-D6-001`。**ID 里不带对象号的用例视为未完成**——多对象混排时，只有它能说清这条在测什么。

不足信息时先问清，再进入 Step 1。

## Step 1 — 需求与业务场景覆盖

**目标：** 做对的事情，防需求漏测。已有书面 Scenario 是基线，不是终态。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. **导入已有 Scenario：** 把该对象下每条书面 Scenario 写成一条 D1 用例，ID、对象、来源（`imported: <Scenario 标题>`）、步骤、预期从原文落地，并标形式。没有书面 Scenario 时，从入口和代码拆该对象可能的业务场景，全部用 `gap:`。导入条数计入批次 1。
2. 对照导入结果，补该对象尚未写成 Scenario 的正向主流程、分支、异常流（取消、失败、中断后重入）。这些缺口用 `gap: <短名>` 作为来源，**不要**写进 RTM。
3. 建 RTM 索引：`需求项 → 已有书面 Scenario → D1 Case ID`（可附相关 D2–D6 ID）。没有书面 Scenario 时 RTM 写「无书面 Scenario，D1 均为 gap:」。RTM 不是第二份用例表：步骤、预期、形式、状态只写在 D1 行上。一个对象不得只停在「导入了现成 Scenario」。
4. 补隐性需求（防重复提交、跨页状态留存等常识逻辑）。

**本步产出表列：** `ID | 对象 | 来源(imported: Scenario / gap: 短名) | 场景类型(正向/分支/异常/隐性) | 步骤 | 预期 | 形式 | 维度=D1`

勾选 Step 1 后进入 Step 2。

---

## Step 2 — 代码与分支覆盖

**目标：** 白盒验证控制流，防未执行代码藏 Bug。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. 标出该对象关键路径上的分支点（if/else、switch、早返回、catch）
2. 为每个判定补 True / False（至少 Branch）
3. 多条件表达式：标出需组合覆盖的条件（高风险再用 Condition Combo / MC/DC）
4. 若有 Git / PR 变更：优先 **Diff Coverage**（本次改动行必须有对应用例）。该对象 Diff 锚点里的每个路径/符号都必须出现在至少一条 D2 代码锚点中，否则写 D2 `不适用` 并说明为何这段 diff 不可测。独立测现有代码、没有本次 diff 时，对该对象关键路径做分支覆盖即可，Diff 锚点写「无本次 diff」。

**本步产出表列：** `ID | 对象 | 代码锚点(文件:符号/分支) | 覆盖类型 | 触发输入 | 预期 | 形式 | 维度=D2`

勾选 Step 2 后进入 Step 3。变异测试不在本步之后立刻跑。

---

## Step 3 — 数据与输入空间覆盖

**目标：** 防特殊数据崩溃与注入。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. 对该对象的每个输入参数做等价类 + BVA（N-1, N, N+1、空、Null、超长）
2. 多参数交互用 pairwise / 正交，避免笛卡尔爆炸
3. 对脏数据测试：SQL/XSS、Emoji、反斜杠、Unicode 特殊字符

**本步产出表列：** `ID | 对象 | 参数 | 等价类/边界/脏数据 | 输入样例 | 预期 | 形式 | 维度=D3`

勾选 Step 3 后进入 Step 4。

---

## Step 4 — 状态变迁与时序覆盖

**目标：** 防非法状态跳跃、竞态、超时重试导致混乱。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. 画出该对象的合法状态与转换（矩阵或列表）
2. 为每条**非法跳跃**设计拒绝/无副作用用例
3. 并发：快速双击、多端同资源
4. 超时与重试：HTTP 超时、MQ 重复投递、幂等性

**本步产出表列：** `ID | 对象 | 状态/时序场景 | 合法? | 操作序列 | 预期 | 形式 | 维度=D4`

勾选 Step 4 后进入 Step 5。

---

## Step 5 — 非功能与防错覆盖

**目标：** 稳、快、安全，不只是「能跑」。

**逐步动作（对每个已登记对象各跑一轮 10→10→10；按对象裁剪，但须显式说明跳过理由）：**
1. 性能：峰值 / 稳态 / 容量（至少标出是否适用）
2. 安全：水平/垂直越权、未授权访问、敏感数据脱敏
3. 容灾：断网、依赖宕机、DB 延迟、第三方 502/504
4. 兼容：OS / 浏览器 / 分辨率 / 弱网（若适用）

**本步产出表列：** `ID | 对象 | 质量属性 | 场景 | 判定标准 | 形式 | 维度=D5`

勾选 Step 5 后进入 Step 6。

---

## Step 6 — 环境与上下文依赖覆盖

**目标：** 防微服务「蝴蝶效应」。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. 列出该对象的上下游依赖（HTTP / MQ / DB / 缓存 / 第三方）
2. 下游延迟/故障：熔断、降级、超时是否生效
3. 数据一致性：分布式事务失败补偿（TCC/Saga 等）是否生效
4. 空数据 / 缓存未命中 / 依赖返回异常时的上游行为

**本步产出表列：** `ID | 对象 | 依赖 | 故障注入 | 期望隔离/补偿 | 形式 | 维度=D6`

勾选 Step 6 后进入 Step 7。若本轮仅产出用例矩阵、尚无自动化，可标注「Step 7 延后」并进入 Step 8，但不得声称单元测试质量已验证。

---

## Step 7 — 变异测试（测试质量门禁）

**目标：** 检验单元测试是否真能抓住缺陷，揭穿「行覆盖高但断言弱」的假覆盖。这是覆盖质量门禁，不是新需求发现手段，也不只验证 D2。

**执行时机：** Step 1–6 全部跑完，且其中所有 `form=unit`（含组件单测）用例已落地、全部通过之后。不要在只写完 D2 时就跑。

**分批覆盖：** 不适用 10→10→10；按变异测试流程执行，对已落地的 **全部 unit 用例** 做质量验证（D2 分支、D3 边界、以及其他维里标了 `unit` 的用例）。integration / E2E 不纳入本步变异范围。

**前置条件（全部满足才跑）：**
1. Step 1–6 中计划为 `unit` 的用例已落地为可执行测试且全部通过（All Green）
2. 测试能红能绿，且含有意义的 Assert（不只是「不抛错」）
3. 行/分支或 Diff 覆盖已达当前约定门槛

**逐步动作：**
1. 应用变异算子（Apply Mutation Operators），制造突变体
2. 针对每个变异体运行测试（Run Tests against Mutants）
3. 判定变异体状态（Determine Mutant Status）, 计算变异得分
    - 变异得分 (Mutation Score)= 被杀死的变异体数 (Killed)/ (生成的总有效变异体数 (Total Valid Mutants)− 等价变异体数 ) 
4. 分析幸存体与排查“等价变异体”

**本步产出：**
- 变异范围（文件/符号）
- 变异得分 + 存活 mutant 列表（各附补测用例 ID 或「等价变异/可忽略」理由）
- 是否达到门禁（未达则不得勾选 Step 7）

勾选 Step 7 后进入 Step 8。发布前可对 Diff 核心模块再跑一次轻量变异，结果并入 Step 8/9。

## Common Mistakes

| 错误 | 纠正 |
|------|------|
| 六维一次写完、无进度勾选 | 停：按 Step 1→6 逐维输出并勾选 |
| 单步用例不足 10 条就进下一步 | 每个对象 × 每个 Step 的批次 1 必须满 10 条（或写明该对象本维动作项已穷尽） |
| 凑数重复用例刷满 30 条 | 每批先去重；去重后 0 新增必须停止扩批 |
| 只有 Happy Path | 强制补异常流 + 非法状态 + 脏数据 |
| 跳过 D2 因为「黑盒」 | 至少标关键分支；有 diff 时钉住 Diff 改动点 |
| 无测试/无断言就跑变异 | 先完成 Step 1–6 中全部 `unit` 用例与覆盖门槛且全绿，再进 Step 7 |
| 只写完 D2 就跑变异 | 停下：D3 等维的 unit 用例也要先绿；Step 7 在 Step 6 之后 |
| 在 E2E/混沌阶段做全仓变异 | 仅对 Diff/核心单元测试层做；场景维靠 D3–D6 设计 |
| Checklist 全勾但无用例 ID | 每项必须挂用例 ID 或「不适用+理由」 |
| 六维压成一张宽表交付 | 按维分成六张表，各用该维 Step 的产出表列 |
| 有书面 `### Requirement:` 却另造一套功能划分 | Step 0 直接取那些 Requirement 为 R1…Rn；已有 Scenario 导入 D1 |
| 没有 spec 就认为本技能不能用 | 从 PRD / 代码 / 入口拆对象后照常跑六维 |
| 把本技能写成只服务 Superpowers 变更 | 独立调用与变更提案共用同一套 Step |
| 只把 spec/PRD 原文转成用例就停 | 导入是基线；必须按 10→10→10 补 `gap:`；漏写的整块能力续编对象 |
| 把入口/文件/Scenario 当成测试对象 | Object 只是需求/能力的 ID；测的是 Entry Point；Scenario 是导入清单 |
| 在 RTM 里再写一遍 D1 的步骤/预期/形式/状态 | RTM 只做书面 Scenario → D1 Case ID 索引；缺口用例用 `gap:` 只出现在 D1 |
| 断言弱到实现写错也能绿 | Expected 必须是会随错误实现而改变的值/状态/协作者 |
| 用例 ID 不带对象号，看不出在测哪条需求 | 一律 `TC-R<n>-D<m>-<seq>`，各表带「对象」列 |
| 只导入现成 Scenario 就宣称 D1 完成 | 导入只是批次 1 的起点；每个对象仍须按 10→10→10 扩到本维穷尽 |
| 六维混成一轮 10 条，多个对象共用配额 | 每个对象 × 每个 Step 各自独立跑 10→10→10 |
| 用例不标形式，或把本可单测的分支写成 E2E | 每条标 `unit` / `integration` / `E2E` ；能在低层观察到的行为就在低层测 |
| 忽略依赖故障 | D5/D6 至少各有一条故障注入 |
