# Full QA Test — 六维立体覆盖

对测试对象做无死角拆解：按固定 Step **逐维**产出用例，禁止跳步、禁止六维混写成一坨。

## When to Use

- 变更提案处于 verify 阶段 / PR 合并需要测试方案或用例
- 发布前担心漏测、要做覆盖自查
- 用户提到：无死角、全覆盖、六维、边界/状态机/并发/降级/变异测试

违反即视为未完成：跳过某一维、只写 Happy Path、用「应该差不多」代替 Checklist。

## principle

执行 `full-qa-test` 各 Step 时按需查阅本文件。维度互补，缺一不可。

     ▼                           ▼                           ▼
┌──────────────┐         ┌──────────────┐         ┌──────────────┐

└──────────────┘         └──────────────┘         └──────────────┘

<Core-principle> 
没有走完六维 Step + 自查 Checklist，就不能声称「覆盖充分」。
如果在测试计划设计阶段, 不需要等待测试结果
如果在测试覆盖阶段, 验证阶段, 必须完成各个step的全部动作, 且测试全部通过才可进入下一阶段(除非该测试无法执行或不适用)
Step 1–6 产出用例时，必须遵循下方「10→10→10 分批覆盖法」。
</Core-principle> 

## 10→10→10 分批覆盖法

**适用：** Step 1–6 产出用例时强制执行，**以「测试对象 × Step」为单位**——每个已登记对象在每个 Step 各独立跑一轮 10→10→10。Step 0 / 2b / 7 / 8 不适用。

**核心规则：** 针对当前对象、当前 Step，先编写 **10 条**用例；若本批经去重后仍有逻辑上非重复的有效用例，再编写 **10 条**；以此类推，**单对象单维最多 30 条**。

### 执行流程

1. **批次 1（必做）：** 针对当前 Requirement，严格按本 Step「逐步动作」产出 10 条用例，覆盖该对象在本维的 P0 / 核心场景。Step 1 先导入该 Requirement 已有的 `Scenario:`，导入条数计入这 10 条，不够再补。没有对应的Scenario 时才手工拆
2. **去重审查：** 逐条对照本对象本维已有用例，判定逻辑是否重复
3. **批次 2（条件允许）：** 若批次 1 去重后 **≥1 条** 为有效新增 → 再产出 10 条，覆盖次要分支 / 边界 / 组合
4. **批次 3（条件允许）：** 若批次 2 去重后 **≥1 条** 为有效新增 → 再产出 10 条，覆盖长尾 / 罕见 / 交叉场景
5. **停止条件（满足任一即停，换下一个对象；本 Step 全部对象跑完才进入下一 Step）：**
   - 本对象本维累计已达 30 条
   - 当前批次去重后 **0 条** 有效新增（无法产出非重复用例）
   - 本对象在本维的动作项已全部覆盖且无合理扩批空间（须写明理由）
   - 本对象在本维确实不适用（写明「R<n> 本维不适用 + 理由」占位，不算欠账）

### 关于体量

对象数 × 6 维 × 至少 10 条会迅速膨胀，这是「无死角」的代价，但**不是要求你凑数**。对象拆得越细，单个对象在某一维的动作项就越容易在批次 1 内穷尽，从而合法触发停止条件。去重规则永远优先于条数：宁可写明「批次 1 仅 6 条，本对象本维动作项已穷尽」，也不要制造 4 条逻辑重复用例把数字填到 10。

### 逻辑重复判定（去重标准）

两条用例视为**逻辑重复**，当且仅当同时满足：

- **输入语义相同**（等价输入 / 等价前置，含边界同类）
- **触发路径相同**（同一操作序列或同一代码分支）
- **断言焦点相同**（验证同一行为 / 同一失败模式）

仅改措辞、换 ID、或只改非关键字段值 → 不算新用例。去重后删除或合并重复项，再计数是否扩批。

### 每 Step 分批进度（产出用例时复制勾选）

```
对象 R<n> · Step N 分批进度:
- [ ] 批次 1 — 10 条（必做）
- [ ] 去重审查 — 有效新增: __ 条 / 剔除重复: __ 条
- [ ] 批次 2 — 10 条（去重后仍有新增才做）
- [ ] 去重审查 — 有效新增: __ 条 / 剔除重复: __ 条
- [ ] 批次 3 — 10 条（去重后仍有新增才做）
- [ ] 去重审查 — 有效新增: __ 条 / 剔除重复: __ 条
- [ ] 本对象本步合计: __ 条（上限 30）— 停止原因: __
```

每批产出后先输出该批用例表 + 去重结论，再决定是否进入下一批；一个对象跑完换下一个对象；本 Step 全部对象跑完后，再勾选 Progress Tracker 对应 Step。

## 测试形式选择

每条用例都必须标注**形式**，取值：`unit` / `integration` / `E2E` 。不标形式的用例无法排期，也看不出证据该长什么样。

**选择原则：能在低层观察到的行为就在低层测。** 只有当行为在低层根本不显现时才上移一层，并在用例里说明为什么必须上移。为了"更真实"把本可单测的分支写成 E2E，是拖慢反馈、制造脆弱用例的主要原因。

| 维度 | 默认形式 | 何时上移 |
|------|----------|----------|
| D1 需求与业务场景 | integration | 价值链跨多个服务，或只有经 UI 才能观察到 → E2E |
| D2 代码与分支 | unit | 分支只有接入真实依赖后才可达 → integration |
| D3 数据与输入空间 | unit | 校验发生在框架/网关层而非被测函数内 → integration |
| D4 状态变迁与时序 | integration | 并发与幂等需要真实存储或队列；跨端竞态 → E2E |
| D5 非功能与防错 | integration | 性能与容量 → 专门压测；兼容性与弱网 → E2E |
| D6 环境与上下文依赖 | integration（故障注入 / 契约测试） | 熔断降级只在完整拓扑下可观察 → E2E |



## Progress Tracker（必须复制并勾选）

**每个step中， 完成一维勾一项，再进入下一维**：

```
六维覆盖进度:
- [ ] Step 0 锁定测试对象
- [ ] Step 1 需求与业务场景
- [ ] Step 2 代码与分支
- [ ] Step 2b 变异测试（测试质量门禁）
- [ ] Step 3 数据与边界
- [ ] Step 4 状态与时序
- [ ] Step 5 非功能与防错
- [ ] Step 6 环境与依赖
- [ ] Step 7 自查 Checklist
- [ ] Step 8 交付测试矩阵
```

每完成一维：对每个已登记 Requirement 各跑一轮 **10→10→10**（含分批进度与去重结论），全部对象跑完再勾选对应 Step，然后才进入下一维。

## Step 0 — 锁定测试对象

**目标：** 明确「测什么」，避免后续维度空转。

**必须产出：**
1. 输入来源（delta spec / PRD / 代码 / OpenAPI / 用户描述）
2. **测试对象登记表**（见下）——把测试范围拆成可独立指认的对象，逐个编号
3. 每个对象一句话风险假设（最可能漏测什么）

### 优先复用已有 spec

变更若带 delta spec（`superpowers/changes/<change>/specs/<capability>/spec.md`），**测试对象直接取自其中的 `### Requirement:`，不要另造一套功能划分**。一条 Requirement 一个对象编号 R1…Rn；某条 Requirement 内部确有可独立指认的子能力时，再拆成 R1a / R1b。

其中的 `#### Scenario:` 是需求方已经构思好的验收场景，**它们就是 D1 的现成基线**：Step 1 直接导入，不要重写一遍。六维的价值在于找出这些 Scenario **没覆盖到**的部分，而不是把它们换个说法再写一次。

没有 spec 时（本技能用于 spec 之外的场景），手工把测试范围拆成可独立指认的能力，同样逐个编号。

### 测试对象登记表（必须产出）

**不登记就直接写用例，是后续「不知道这条在测什么」的根因。** 只有一个对象时也要登记一行。

| 对象 | 需求项 | 已有 Scenario | 入口 | Diff 锚点 | 风险假设 |
|------|--------|---------------|------|-----------|----------|
| R1 | `Requirement: 订单取消` | 3 条：待支付可取消 / 已发货拒绝 / 中断后可重试 | `POST /api/orders/{id}/cancel` | `orderService.ts:cancel` | 退款失败时留下半取消状态 |
| R2 | `Requirement: 取消原因审计` | 1 条：取消成功写审计 | `AuditLog.record`（由 R1 触发） | `auditLog.ts:record` | 取消成功但审计静默失败，无人发现 |

- **需求项**：spec 里的 Requirement 原名，便于回溯；无 spec 时写能力名
- **已有 Scenario**：该 Requirement 下已写好的 Scenario 条数与要点，Step 1 的导入清单
- **入口**：外部真正能调到它的地方（HTTP 路由 / CLI 子命令 / 导出函数 / UI 路由），不是内部实现名
- **Diff 锚点**：本次改动落在哪些文件或符号上；纯新增写新文件名
- 对象之间若有触发关系（如 R1 触发 R2），在风险假设里点明

### 用例 ID 规范

Step 1–6 的每条用例 ID 一律为 `TC-R<对象号>-D<维度号>-<序号>`，例如 `TC-R2-D6-001`。**ID 里不带对象号的用例视为未完成**——多对象混排时，只有它能说清这条在测什么。

不足信息时先问清，再进入 Step 1。

## Step 1 — 需求与业务场景覆盖

**目标：** 做对的事情，防需求漏测。已有 `Scenario:` 是基线，不是终态。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. **导入已有 Scenario：** 把该 Requirement 下每条 `Scenario` 写成一条 D1 用例，ID、对象、需求项、步骤、预期都从 spec 原文落地，并标形式。没有Scenario时, 考虑该需求可能的业务场景。 导入条数计入批次 1。
2. 对照导入结果，补该对象尚未写成 Scenario 的正向主流程、分支、异常流（取消、失败、中断后重入）。
3. 建 RTM：`Requirement → 已有 Scenario + 本步新增用例`。一条 Requirement 不得只停在「导入了现成 Scenario」。
4. 补隐性需求（防重复提交、跨页状态留存等常识逻辑）。

**本步产出表列：** `ID | 对象 | 需求项 | 场景类型(正向/分支/异常/隐性) | 步骤 | 预期 | 形式 | 维度=D1`

勾选 Step 1 后进入 Step 2。

---

## Step 2 — 代码与分支覆盖

**目标：** 白盒验证控制流，防未执行代码藏 Bug。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. 标出该 Requirement 关键路径上的分支点（if/else、switch、早返回、catch）
2. 为每个判定补 True / False（至少 Branch）
3. 多条件表达式：标出需组合覆盖的条件（高风险再用 Condition Combo / MC/DC）
4. 若有 Git 变更：优先 **Diff Coverage**（本次改动行必须有对应用例）

**本步产出表列：** `ID | 对象 | 代码锚点(文件:符号/分支) | 覆盖类型 | 触发输入 | 预期 | 形式 | 维度=D2`

勾选 Step 2 后进入 Step 2b（有可运行测试时）；若本轮仅产出用例矩阵、尚无自动化，可标注「2b 延后」并进入 Step 3，但不得声称 D2 测试质量已验证。

---

## Step 2b — 变异测试（测试质量门禁）

**目标：** 检验用例是否真能抓住缺陷，揭穿「行覆盖高但断言弱」的假覆盖。属于 **D2 的覆盖质量验证**，不是新需求发现手段。

**分批覆盖：** 不适用 10→10→10；按变异测试流程执行，对 Step 2 已落地用例做质量验证。

**前置条件（全部满足才跑）：**
1. Step 2 用例已落地为可执行测试（单元/组件优先）且全部通过（All Green）
2. 测试能红能绿，且含有意义的 Assert（不只是「不抛错」）
3. 行/分支或 Diff 覆盖已达当前约定门槛

**逐步动作：**
1. 应用变异算子（Apply Mutation Operators），制造突变体
2. 针对每个变异体运行测试（Run Tests against Mutants）
3. 判定变异体状态（Determine Mutant Status）, 计算变异得分
    - 变异得分 (Mutation Score)= 被杀死的变异体数 (Killed)/ (生成的总有效变异体数 (Total Valid Mutants)− 等价变异体数 ) 
​4. 分析幸存体与排查“等价变异体”

**本步产出：**
- 变异范围（文件/符号）
- 变异得分 + 存活 mutant 列表（各附补测用例 ID 或「等价变异/可忽略」理由）
- 是否达到门禁（未达则不得勾选 2b）

勾选 Step 2b 后进入 Step 3。发布前可对 Diff 核心模块再跑一次轻量变异，结果并入 Step 7/8。

---

## Step 3 — 数据与输入空间覆盖

**目标：** 防特殊数据崩溃与注入。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. 对该 Requirement 的每个输入参数做等价类 + BVA（N-1, N, N+1、空、Null、超长）
2. 多参数交互用 pairwise / 正交，避免笛卡尔爆炸
3. 对脏数据测试：SQL/XSS、Emoji、反斜杠、Unicode 特殊字符

**本步产出表列：** `ID | 对象 | 参数 | 等价类/边界/脏数据 | 输入样例 | 预期 | 形式 | 维度=D3`

勾选 Step 3 后进入 Step 4。

---

## Step 4 — 状态变迁与时序覆盖

**目标：** 防非法状态跳跃、竞态、超时重试导致混乱。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. 画出该 Requirement 的合法状态与转换（矩阵或列表）
2. 为每条**非法跳跃**设计拒绝/无副作用用例
3. 并发：快速双击、多端同资源
4. 超时与重试：HTTP 超时、MQ 重复投递、幂等性

**本步产出表列：** `ID | 对象 | 状态/时序场景 | 合法? | 操作序列 | 预期 | 形式 | 维度=D4`

勾选 Step 4 后进入 Step 5。

---

## Step 5 — 非功能与防错覆盖

**目标：** 稳、快、安全，不只是「能跑」。

**逐步动作（对每个已登记对象各跑一轮 10→10→10；按对象裁剪，但须显式说明跳过理由）：**
1. 性能：峰值 / 稳态 / 容量（至少标出是否适用）
2. 安全：水平/垂直越权、未授权访问、敏感数据脱敏
3. 容灾：断网、依赖宕机、DB 延迟、第三方 502/504
4. 兼容：OS / 浏览器 / 分辨率 / 弱网（若适用）

**本步产出表列：** `ID | 对象 | 质量属性 | 场景 | 判定标准 | 形式 | 维度=D5`

勾选 Step 5 后进入 Step 6。

---

## Step 6 — 环境与上下文依赖覆盖

**目标：** 防微服务「蝴蝶效应」。

**逐步动作（对每个已登记对象各跑一轮 10→10→10）：**
1. 列出该 Requirement 的上下游依赖（HTTP / MQ / DB / 缓存 / 第三方）
2. 下游延迟/故障：熔断、降级、超时是否生效
3. 数据一致性：分布式事务失败补偿（TCC/Saga 等）是否生效
4. 空数据 / 缓存未命中 / 依赖返回异常时的上游行为

**本步产出表列：** `ID | 对象 | 依赖 | 故障注入 | 期望隔离/补偿 | 形式 | 维度=D6`

勾选 Step 6 后进入 Step 7。

## Step 7 — 无死角自查 Checklist

对照下表逐项勾选；未覆盖项必须补用例或写明「不适用 + 理由」：

| 维度 | 必查项 | 覆盖? | 补充用例 ID / 说明 |
|------|--------|-------|-------------------|
| 功能 | 1. 正向主流程及所有分支逻辑 | [ ] | |
| 功能 | 2. 异常中断后恢复机制 | [ ] | |
| 代码 | 3. Diff/关键路径分支覆盖 + 变异测试（或「延后/不适用」理由） | [ ] | |
| 数据 | 4. 边界值（最大/最小/0/负/空串/Null） | [ ] | |
| 数据 | 5. 特殊字符、超长、Emoji、SQL/XSS | [ ] | |
| 状态 | 6. 状态机非法路径（越权/逆向切换） | [ ] | |
| 状态 | 7. 并发请求及幂等（双击/重放） | [ ] | |
| 依赖 | 8. 第三方超时/5xx 时降级兜底 | [ ] | |
| 依赖 | 9. DB/缓存为空或异常时的逻辑 | [ ] | |
| 环境 | 10. 弱网（高延迟/高丢包/无网） | [ ] | |
| 环境 | 11. 多终端/分辨率/权限角色兼容 | [ ] | |

任一项未勾且无「不适用」理由 → 回到对应 Step 补齐。

**逐项按 Requirement 核对，不要整体勾。** 上表每项都要对所有已登记对象成立：某项只有 R1 有用例、R2 既没有用例也没写「本维不适用 + 理由」，该项不得勾选。补充说明列写清各对象的用例 ID，例如 `R1: TC-R1-D3-001/002；R2: TC-R2-D3-001`。

### Requirement × 维度覆盖矩阵（多对象时必须产出）

登记了两个及以上 Requirement 时，额外产出这张矩阵，一眼看出哪条需求在哪一维空着：

| 对象 | D1 | D2 | D3 | D4 | D5 | D6 |
|------|----|----|----|----|----|----|
| R1 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| R2 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

单元格填 `✓`（有用例）或 `N/A + 理由`；空单元格即欠账，回到对应 Step 补齐。

勾选 Step 7 后进入 Step 8。

## Step 8 — 交付输出包

### 分维用例表 — 示例（格式示范，交付时替换为 Step 0–6 实际产出）

**六维分表交付，不要合并成一张宽表。** 每维沿用该维 Step 的产出表列，各维列不同是有意的：混在一张表里，多数列对多数行都是空的，既难读也难审。

**每张表都带「对象」列和「形式」列，ID 也带对象号。** 示例刻意用两条 Requirement，演示混排时如何指认；一维内多个对象的行按对象号聚拢排列。D1 前几行是从 spec `#### Scenario:` 导入的基线，后面才是本维补出的缺口。

> 本轮 Step 0 登记：**R1 `Requirement: 订单取消`**（已有 3 条 Scenario；入口 `POST /api/orders/{id}/cancel`，锚点 `orderService.ts:cancel`）、**R2 `Requirement: 取消原因审计`**（已有 1 条 Scenario；`AuditLog.record`，由 R1 触发，锚点 `auditLog.ts:record`）

### 输出格式

**最终回复必须包含（按此顺序）：**

1. **测试对象登记表与风险摘要**（来自 Step 0：每条 Requirement 一行，含已有 Scenario、入口与 Diff 锚点）
2. **六张分维用例表**（D1–D6 各一张，沿用各维 Step 的产出表列，每张带「对象」和「形式」列；不要合并成一张宽表）
3. **RTM**（Requirement → 已有 Scenario + 用例 ID 列表）
4. **自查 Checklist**（Step 7 已填）+ **Requirement × 维度覆盖矩阵**（登记了两个及以上 Requirement 时必须给出）
5. **自动化骨架**（可选但推荐）：AAA 格式，含断言；优先覆盖 P0（主流程、非法状态、幂等、依赖降级）
6. **变异测试结果**（若执行了 2b）：范围、杀伤率、存活 mutant 与补测 ID；未跑则写「延后/不适用 + 理由」
7. **残留风险**：明确未自动化 / 需人工 / 环境受限 / 未杀死 mutant 项

完成后勾选 Step 8。未完成进度清单不得声称「全覆盖完成」。


## Common Mistakes

| 错误 | 纠正 |
|------|------|
| 六维一次写完、无进度勾选 | 停：按 Step 1→6 逐维输出并勾选 |
| 单步用例不足 10 条就进下一步 | 每个 Requirement × 每个 Step 的批次 1 必须满 10 条（或写明该对象本维动作项已穷尽） |
| 凑数重复用例刷满 30 条 | 每批先去重；去重后 0 新增必须停止扩批 |
| 只有 Happy Path | 强制补异常流 + 非法状态 + 脏数据 |
| 跳过 D2 因为「黑盒」 | 至少标关键分支与 Diff 改动点 |
| 无测试/无断言就跑变异 | 先完成 Step 2 可执行用例与覆盖门槛，再进 2b |
| 在 E2E/混沌阶段做全仓变异 | 仅对 Diff/核心单元测试层做；场景维靠 D3–D6 设计 |
| Checklist 全勾但无用例 ID | 每项必须挂用例 ID 或「不适用+理由」 |
| 六维压成一张宽表交付 | 按维分成六张表，各用该维 Step 的产出表列 |
| 变更已有 delta spec 却另造一套功能划分 | Step 0 直接取 `### Requirement:` 为 R1…Rn；已有 Scenario 导入 D1 |
| 用例 ID 不带对象号，看不出在测哪条需求 | 一律 `TC-R<n>-D<m>-<seq>`，各表带「对象」列 |
| 只导入现成 Scenario 就宣称 D1 完成 | 导入只是批次 1 的起点；每个 Requirement 仍须按 10→10→10 扩到本维穷尽 |
| 六维混成一轮 10 条，多条需求共用配额 | 每个 Requirement × 每个 Step 各自独立跑 10→10→10 |
| 用例不标形式，或把本可单测的分支写成 E2E | 每条标 `unit` / `integration` / `E2E` ；能在低层观察到的行为就在低层测 |
| 忽略依赖故障 | D5/D6 至少各有一条故障注入 |
