# 技术原理学习笔记

## 核心目标

把一个真实的 bug 原理、实现机制或技术决策，提炼成一篇可迁移的学习笔记。

将代码当作事实依据，不把笔记写成源码导览、调用链清单或业务模块文档。正文应帮助读者建立一个可复用的心智模型：问题是什么、机制如何工作、为什么必须这样设计、哪些边界会破坏它。

## 写作流程

### 1. 收窄为一个研究对象

- 只回答一个细节问题，例如“为什么必须先授权再读取对象”或“为什么打包结果会产生多个 chunk”。
- 用一个机制或一个因果问题命名标题；不要用整个模块名作为标题。
- 如果用户的问题过宽，选择最有技术含量的一段并明确排除相邻内容。

### 2. 读取代码，但只提取必要事实

- 只阅读能解释该机制的函数、测试、配置和数据结构。
- 区分三类内容：代码明确表现出的事实、根据事实推导出的原理、适用于一般系统的经验。
- 不把文件路径、行号、函数调用顺序写成正文主线。源码信息默认只作为分析依据；确实需要复查时，在文末用不超过三条的“实现依据”简短列出即可。
- 代码不足以证明某个结论时，标记假设或不确定性，不要补写不存在的行为。

### 3. 建立技术解释模型

按以下顺序分析：

1. 明确问题本质、约束条件或被破坏的不变量。
2. 抽象出输入、状态/数据、决策、输出之间的关系。
3. 用最小伪代码或小段代码展示机制，不做逐行翻译。
4. 解释关键顺序、责任边界和数据为何必须从某一层取得。
5. 对比一个看似更简单但不可靠的方案，说明它为什么失败。
6. 只讨论与核心机制直接相关的少量边界和取舍。

如果主题来自 bug，使用这条因果链：

```text
现象 → 被破坏的不变量 → 根因 → 修复为何改变行为
```

### 4. 用 Excalidraw 图示辅助阐述

机制涉及顺序、边界或多方交互时，**必须**配至少一张 Excalidraw 图；纯概念定义且无可视化收益时可省略。

| 图类型 | 适用场景 |
|--------|----------|
| 流程图 | 决策分支、状态迁移、因果链、修复前后路径对比 |
| 时序图 | 调用/授权/异步的先后约束、竞态、消息往返 |
| 框架图 | 组件职责、数据从哪一层来、模块边界与依赖方向 |
| 对比图 | 可靠方案 vs 看似更简单但会失败的方案 |

**绘制与产出：**

- 使用 Excalidraw（Cursor/VS Code 的 `pomdtr.excalidraw-editor` 扩展，或 excalidraw.com）绘制。
- 图示文件与笔记同目录，命名 `{主题-slug}-{图类型}.excalidraw.svg`（或 `.excalidraw.png`），便于在 Markdown 中引用且保留可编辑场景数据。
- 在笔记正文中用 `![图注说明](文件名.excalidraw.svg)` 嵌入；图注一句话说明「这张图帮读者看清什么」。
- 图中只保留与当前机制相关的节点与箭头；标注关键顺序、边界名称和被破坏的不变量，不写文件路径或行号。
- 一张图只表达一个视角；流程 + 时序各需一张时，拆成两个文件，不在一张图里堆叠多种语义。
- 优先于 ASCII/Mermaid：本技能产出默认可编辑、可复用的 Excalidraw 资产；仅在无法创建 `.excalidraw.*` 文件时用 Mermaid 作临时替代并注明。

## 内容边界与表达要求

- 使用简体中文；保留必要的英文技术术语。
- 以原理分析为主，以代码片段为证据；不要堆叠完整项目代码。
- 默认不插入项目文件链接、行号、调用位置和模块目录说明。
- 不罗列大量业务场景、角色组合、接口清单或测试用例；场景只有在证明一个技术边界时才出现。
- 不把“常见问题”“生产环境注意事项”扩展成与主题无关的百科全书。
- 不写成需求文档、架构模块文档、代码审查报告或测试报告。
- 解释每段伪代码解决的技术问题，并说明它依赖的前提。
- 图示与文字分工：文字讲「为什么」，图示讲「关系与顺序」；避免用长段落重复图中已有信息。

## 输出前检查

- 能否用一句话说清这篇笔记只研究哪一个机制？
- 正文是否解释了“为什么”，而不只是说明“调用了什么”？
- 是否包含最小实现模型和至少一个设计取舍？
- 是否把直接相关的边界控制在一到三个？
- 删除文件路径、行号和业务场景后，技术解释是否仍然成立？
- 是否区分了代码事实、原理推导和一般化结论？
- 涉及顺序、边界或交互时，是否已有 Excalidraw 图且图注说清了读者应带走的心智模型？
- 每张图是否只承担一种视角（流程 / 时序 / 框架 / 对比），且未混入项目路径或无关节点？
