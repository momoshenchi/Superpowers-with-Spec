# 技术原理学习笔记

## 核心目标

从一次具体 bug 出发，把它**归纳**成一类经典通用问题，写成可迁移的学习笔记。

不是先找一个问题名再往上套，而是先看清这次出了什么事，再问：去掉产品外壳后，剩下的结构是哪类已知问题？例如多处写卡片落库、互相覆盖或冲突，归纳为**双写者问题**。

代码是证据，不是正文主语。开篇可以用这次 bug 作引子；正文展开的是那类经典问题：机制如何工作、为什么必须这样、和相邻经典问题如何切开。

```text
这次 bug 里的具体结构                    归纳成的经典问题
多处写入同一份权威数据、互相 409   →   双写者
动作成功拆成两条持久化，刷新绑错管 →   双真相源
在途读取用完成时的 live 进度勾意图 →   陈旧读者（把时钟当成证据）
```

## 产出位置与命名

默认写到：

```text
docs/learning_notes/<classic-problem-slug>/
  README.md
  <slug>-<图类型>.excalidraw.svg
```

- 一文一目录：笔记是 `README.md`，图与笔记同目录，Markdown 用相对路径引用。
- `<classic-problem-slug>` 用经典问题的英文 kebab-case，不用功能名：`dual-writer`，不要 `card-persist-queue`。
- 仓库里若已有 `docs/learning-notes`、`docs/learning_notes` 或 `docs/notes`，沿用已有目录，不要另开一套。
- 不要写到 `superpowers/changes/`、源码旁或临时聊天目录。
- 目录不存在则创建。一篇笔记只对应一个主经典问题；相邻问题在文内切开，不另起混淆的功能目录。

## 写作流程

```text
具体 bug → 抽出共同结构 → 归纳为经典问题 → 落到约定目录
                开篇保留这次 bug，正文展开经典问题
```

### 1. 收窄这次 bug

- 只回答一个因果。过宽则切最有技术含量的一段，并点名不讨论什么。
- 标题写成这次 bug 的机制问题（「为什么在途读取不能用完成时的进度满足后来的写入」），不用模块名、按钮文案、内部 API。

### 2. 从代码抽出具体结构

- 只读能解释该机制的函数、测试、配置和数据结构。
- 此时可以想「哪几处在写卡、哪次读取还在路上」，用来理解因果；这些功能词稍后只留在开篇。
- 抽出最少的结构：几个写者、几条管道、谁先谁后、什么叫「看见」。
- 区分代码事实、由事实推出的原理、一般系统经验。代码不够则标假设，不补写不存在的行为。

### 3. 归纳为经典通用问题

看共同结构，而不是给功能起别名：

- 多个写入打同一份权威数据且未串行 → 双写者
- 已发出的读取用完成时的时钟宣布覆盖了后到的写入 → 陈旧读者
- 一次动作两条持久化，UI 终态绑了刷新后不可靠的那条 → 双真相源

归纳式是：`这次具体发生的事` → `同一结构的经典名字`。还停在「落卡 HTTP 和 persist 排队」说明没有归纳完；用一句话写下共同结构再命名。

### 4. 开篇用这次 bug，正文用经典问题

具体现象最多 **2–3 句**，立刻接上归纳句：「这是双写者问题。」之后小节标题、伪代码变量、图中节点都用抽象角色（写者 / 读者 / 时钟 / 证据 / 真相源 A·B）。

| 可以 | 不可以 |
|------|--------|
| 开篇：「连续两次提交后，后一次刷新消失。」 | 全文反复写同一功能名、按钮文案、内部 API |
| 归纳：「多个写入打同一份权威文档。这是双写者问题。」 | 把功能实现复述一遍，当作已经归纳 |
| 收束：「这解决的是双写者问题。上一节解决的是陈旧读者问题。」 | 「这解决的是落卡 HTTP 与 persist 排队。」 |

### 5. 展开机制，并用图讲清关系

不要写成「被破坏的不变量」小节。按这次归纳出的经典问题展开：

1. 写清约束：谁先谁后、谁是权威、什么叫「看见」。
2. 给输入 / 状态 / 决策 / 输出起抽象名。
3. 最小伪代码；变量名是角色，不是产品函数名。
4. 对比一个看似更简单但会失败的方案；失败原因落到经典问题上（「把时钟当成证据」），不是「少写了重试」。
5. 一到三个相邻边界，每个也归纳成经典问题，并用一句切开：`这解决的是 X。上一节解决的是 Y。两者独立，因为……`

```text
现象（这次 bug，极短） → 归纳为经典问题 → 机制 → 修复改变了哪条因果关系 → 与相邻经典问题如何切开
```

正文结构：引子与归纳 → 机制模型（配图） → 最小伪代码 → 错误方案（配对比图） → 相邻问题切开 → 可迁移结论 → 实现依据。

文件路径、行号、调用顺序不是正文主线。文末「实现依据」不超过三条，用机制语言写（「出发时记下观察值」），不要写成 API 清单。

### 6. 图与文件一起落到该目录

顺序、窗口、多方角色或错误对照只要出现，**默认至少两张图**：机制 + 对比；有独立时序窗口再加第三张。纯定义且一张已够时可以只出一张，图注仍必须是经典问题的那句话。

写正文前先列出「读者要带走的句子」，**一句一图**：

| 读者要带走的句子 | 图类型 |
|------------------|--------|
| 谁在什么时刻看见了什么 | 时序图 |
| 可靠路径 vs 把时钟当证据 / 绑错权威 | 对比图 |
| 职责、数据从哪一层来、依赖方向 | 框架图 |
| 两个写者与一个陈旧读者是不同问题 | 角色图 |
| 决策分支、状态迁移 | 流程图 |

- 使用 Excalidraw（`pomdtr.excalidraw-editor` 或 excalidraw.com）。
- 图放在该笔记目录内，命名 `<slug>-<图类型>.excalidraw.svg`（或 `.excalidraw.png`）。
- 正文 `![图注](文件名.excalidraw.svg)`。图注 = 归纳句，例如「live 是时钟，在途观察值才是证据」；不要复述箭头。
- 图中标签用抽象角色，不写路径、行号、按钮文案、内部函数名。一张图一个视角。
- 文字讲「为什么」，图讲「关系与顺序」。无法创建 `.excalidraw.*` 时才用 Mermaid，并注明临时替代。

## 内容边界

- 简体中文；保留必要英文术语。
- 原理为主，代码为证；禁止堆完整项目代码、接口清单、测试用例。
- 不要单独写「被破坏的不变量」章节。约束写进经典问题和机制关系即可。
- 不写成需求文档、模块文档、代码审查或测试报告，也不把「生产注意事项」扩成百科。
- 伪代码之后必须能回答：这段解决的是哪一类经典问题，依赖什么前提。

## 输出前检查

- 文件是否在 `docs/learning_notes/<经典问题-slug>/README.md`（或仓库已有的同等笔记目录）？目录名是经典问题，不是功能名？
- 开篇是否是这次 bug，随后是否有明确的归纳句？
- 删掉开篇后，正文能否只用经典问题讲完？
- 产品功能名、内部 API 是否只出现在开篇？实现依据是否也用机制语言？
- 每个主要小节是否能说清「这解决的是 X。上一节是 Y。」？
- 是否有最小模型和至少一个失败对照？图是否一句一图、图注是归纳句、节点是抽象角色？
